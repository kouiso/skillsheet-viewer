# Dogfooding テスト仕様書

skillsheet-viewer の全画面を実際に操作し、表示データが元データと一致するか、
細部の表示が破綻していないかを判定するための仕様書。

## 1. 目的と非目的

### 目的

1. **データ一致の検証** — 画面に出る値が元データ（`kouiso/skill-sheet` の `skillsheet.md`）および
   正本 DB（Neon Postgres）と一致するか
2. **細部の破綻検出** — 欠落・重複・順序狂い・表崩れ・はみ出し・空表示
3. **画面としての成立** — 余白・整列・コントラスト・階層が破綻していないか

### 非目的

- デザイン正本（Figma / Claude Design）との pixel 単位の突合
- 性能測定・負荷試験
- セキュリティ診断（**ただし A-6a / A-6b の open redirect は機能回帰として実施する**。脆弱性の網羅的な洗い出しはしないが、
  既知の判定式が壊れていないかは毎回確認する）

## 2. 検証環境

| 項目 | 値 |
|---|---|
| ビルド | `pnpm build` → `pnpm start -p 3210`（本番ビルド。dev の HMR ノイズを避ける） |
| DB | Neon 本番プロジェクト `skillsheet-viewer` からのコピーブランチ（本番には書かない） |
| ブラウザ | Chromium（Playwright） |
| ビューポート | 320×800 / 375×812 / 768×1024 / 1280×800 |
| テーマ | light / dark |
| 証跡 | `test-results/dogfooding/<round>/<case-id>-<viewport>-<theme>.png`（1 巡目のみ `dogfooding/` 直下、2 巡目以降は `round2/` `round3/` … と巡回ごとに分ける） |

### 元データと正本の関係

```text
kouiso/skill-sheet/skillsheet.md   ← 元データ（人が書いた一次情報）
          ↓ インポート
Neon Postgres (skill_sheets / blocks) ← 正本（アプリが読む）
          ↓ blocksToMarkdown
     画面表示 / PDF出力
```

画面系のケース（B 章）のデータ突合は **元データ → 正本 → 画面** の 3 点で行う。
正本と画面が一致していても、元データから欠落していれば FAIL とする。

**PDF の内容突合（D-2）だけは 4 点**で行う。画面と PDF はどちらも同じ `blocksToMarkdown` /
構造化ブロックを源にしているため、2 点だけを突き合わせても「両方から同じデータが落ちている」
状態を検出できない。**元データ → 正本 DB → 画面 → PDF** の 4 情報源それぞれについて件数と
中身を記録し、どの段で差分が出たかを特定できる形で残す。

## 3. 判定基準（全ケース共通）

PASS は次を全て満たしたときのみ。

1. **データ一致** — 表示値が元データ・正本と一致する。欠落・重複・順序狂い・文字化けなし
2. **レイアウト** — 横スクロールなし（`scrollWidth <= clientWidth`）。要素の重なり・はみ出し・見切れなし
3. **文字** — 折返し破綻なし。`undefined` / `null` / `NaN` / 裸の `-` が出ない
4. **状態** — ローディング・空状態・エラー状態が意味のある文言で出る
5. **コンソール** — `console.error` ゼロ。`warning` は記録して個別判断
6. **操作** — 押せるものは全て押し、期待どおりの結果になる
7. **見た目** — 撮影画像を必ず開いて確認し、余白・整列・コントラスト・階層を評価する

> BUG が 1 件でもあればそのケースは **FAIL**。「PASS ただしバグあり」は認めない。
> 撮影しただけ・メタデータを見ただけは検証にしない。

## 4. テストケース

### A. 認証・入口

| ID | ケース | 手順 | 期待 |
|---|---|---|---|
| A-1 | 未認証で `/view` | cookie なしで `/view` を開く | `/viewer-auth` へリダイレクトする。クエリの有無は問わない: 2026-08-04 時点の `requireViewer()` は `next` を付けないが、U-6（#155）でゲートが `next` を保持するよう直せば `?next=/view` が付く。**どちらも PASS**。判定するのは「`/viewer-auth` に飛ぶこと」と、`next` が付く場合に**内部パスであること**（外部 URL なら FAIL） |
| A-2 | 閲覧コード誤り | 誤ったコードで認証 | エラー文言が出る。画面が壊れない |
| A-3 | 閲覧コード正 | 正しいコードで認証 | `next` のパスへ戻る |
| A-4 | ログイン誤り | 誤った email / password | 「メールアドレスまたはパスワードが正しくありません」 |
| A-5 | ログイン正 | 正しい credential | `/builder` へ遷移 |
| A-6a | open redirect（`/login`） | `next` に `//evil.example.com` / `https://evil.example.com` / **`/\/evil.example.com`** を与える | いずれも外部へ飛ばず `/builder` へ |
| A-6b | open redirect（`/viewer-auth`） | 同じ 3 パターンを `/viewer-auth?next=` に与える | いずれも外部へ飛ばず `/view` へ。`/login` とは別のパーサ（`viewer-auth/page.tsx`）なので個別に確認する。`\` を含む異表記は 2026-08-04 時点で回避できる（#159）ため、修正の回帰確認に使う |
| A-7 | ログアウト | **閲覧コードだけで認証した独立コンテキスト**で `POST /api/logout` | 閲覧セッションが破棄され、再度ゲートが効く。`/api/logout` は HMAC 閲覧 cookie しか消さず、`requireViewer()` は `isEditor()` でも通すため、A-5 と同じコンテキストで続けて実行すると `/view` はゲートされない（アプリの逸脱ではなく手順の誤り） |

### B. 閲覧（Viewer） — データ突合の本体

| ID | ケース | 検証内容 |
|---|---|---|
| B-1 | `/view` 一覧 | シート枚数・タイトル・更新日時が DB と一致。空/エラー状態の文言 |
| B-2 | `/view/db/:id` 初期表示 | トップバーに profile の氏名・所属会社。4 ビュー全 ON |
| B-3 | profile 突合 | 氏名・肩書き・自己PR・強み・年齢・勤務形態・最寄り駅・学歴に加え、**所属会社・性別・保有資格・得意分野・得意業務**を元データの「技術者プロファイル」節と 1 項目ずつ突合。後半 5 項目は 2026-08-04 時点でいずれも画面に出ていないが、原因が 2 種類あるので分けて確認する（#140）。**所属会社**は `ProfileBlockData.company` と `profile-intro.tsx` の描画が既にあり、インポートが値を入れていないだけ（＝データ投入の問題）。**性別・保有資格・得意分野・得意業務**は `ProfileBlockData` に保存先そのものが無い（＝スキーマの問題）。修正後の回帰でここを素通りさせない |
| B-4 | stats 突合 | 4 枠の数値と単位が元データの記述と矛盾しない |
| B-5 | skills 突合 | 全カテゴリ × 全スキルの「名称・年数・習熟度」を元データのスキル表と全件突合。件数も一致させる |
| B-6 | 案件件数突合 | 画面の会社数・案件数を数え、正本 DB および元データと突合する。**元データ側の数え方を取り違えない**こと: 会社は `^### ◆`（19）、案件は `^#### ■`（32）。案件見出しは連番付き（`#### ■ 3. …`）と連番なし（個人開発配下の 2 件）が混在するので、`\d+\.` を必須にすると 30 件になり取りこぼす。件数だけでなく**タイトル文字列も全件突合**する（#160 のように件数一致のまま中身が短くなる欠落があるため） |
| B-7 | 案件詳細突合 | 全案件について 期間・役割・規模・チーム・技術スタック・担当工程・業務内容・習得スキルを元データと突合（サンプリング禁止・全件） |
| B-8 | 期間表記 | 期間・年数の表示が元データと一致。「継続中」案件の表記 |
| B-9 | ビュートグル | スキルマトリクス / 工程の俯瞰 / 案件詳細 / タイムライン を個別 OFF→ON。全 OFF 時の見た目 |
| B-10a | 目次（DB の markdown ブロック） | 項目が見出しと一致。スクロールでアクティブ見出しが追従（`aria-current`）。**markdown ブロックを含む `/view/db/:id`** が対象で、GitHub 経路が使えない環境でも実行できるのでこちらを主対象にする。除外するのは**構造化ブロックだけのダッシュボード**で、`SectionHead` が意図的に id を付けず `headings.length === 0` になり TOC を描画しないため。**アクティブ追従を測るときは見出しを十分離す**こと（密集していると複数が同時に観測帯 `rootMargin: '-100px 0px -66% 0px'` に入り 1:1 で判定できない） |
| B-10b | 目次（`/view/[path]` 経路） | 同上を旧経路でも確認する。旧経路は `SkillSheetViewer` を `blocks` 未指定で描画するため別コードパスで、B-10a では代替できない |
| B-11 | 技術フィルタ | 絞り込みで該当案件のみ残る。0 件時の表示 |
| B-12 | 工程ステッパー | 表示される工程が案件の `process` と一致 |
| B-13a | Markdown 描画（構造化ブロック） | 案件の `summary` / `duties` / `comment` の箇条書き・強調が描画される |
| B-13b-1 | Markdown 描画（DB の markdown ブロック） | GFM 表が表として描画される（`:---:` の生テキスト露出なし）。`<details>` の開閉。`/view/db/:id` も `blocks` を `SheetViewClient` に渡し、同じ ReactMarkdown + remark-gfm 経路を通るので**こちらを主対象にする**（GitHub 経路が使えない環境でも実行できる） |
| B-13b-2 | Markdown 描画（`/view/[path]` 経路） | 同上を旧経路でも確認する。旧経路は `blocks` 未指定で描画されるため別コードパス |
| B-14 | 存在しない ID | `/view/db/<random-uuid>` で 404 ページ |
| B-15a | `/view/[path]`（env 未設定時の案内） | GitHub 連携未設定時に 500 でなく、原因と対処が分かる案内が出る。`/compare` の文言と食い違わないこと |
| B-15b | `/view/[path]`（markdown シートの描画） | GitHub の実トークンを設定し、markdown シートが描画される |
| B-16 | `/compare` | a/b 欠落時は `/view` へ。2 枚並列表示。狭幅で縦積み。**`/view` の一覧から選べる DB シートの id 同士を比較できること**を期待に含める（GitHub 由来の `.md` パス同士だけが動く状態を PASS にしない。2026-08-04 時点では DB シートを受け付けない＝U-2 / #145） |

## 5. 記録フォーマット

各ケースについて次を記録する。

```text
[ケースID] 結果: PASS / FAIL / BLOCKED
  スクリーンショット: <path>（開いて確認済み）
  観察: 画面上の要素列挙 + レイアウト記述
  突合（画面系 B 章）: 元データ → 正本 DB → 画面 の件数と中身 → どの段で差が出たか
  突合（D-2 のみ）: 元データ → 正本 DB → 画面 → PDF の件数と中身 → どの段で差が出たか
  逸脱: BUG / COSMETIC の分類（最終判断はレビュアー）
```

## 6. 逸脱の扱い

- 原則 1 逸脱 = 1 Issue。`.github/ISSUE_TEMPLATE/bugfix.yml` / `feature.yml` の構成に合わせる
- ただし、単独では着手単位にならない小さな逸脱（同一ファイルの細部・同種のコントラスト不足など）は
  1 Issue にまとめてよい。まとめた場合は Issue 本文に逸脱を見出しで分けて列挙し、
  完了条件も逸脱ごとにチェックボックスを立てる（個別に潰せる状態を保つ）
- 期待挙動・実際の挙動・再現手順・スクリーンショットを必ず入れる
- 全 Issue を束ねる親 Issue（dogfooding 結果サマリ）を 1 本立てる
- 修正は別タスク。この仕様書の実行範囲は起票までとする

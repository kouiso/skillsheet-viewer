# Dogfooding テスト仕様書

skillsheet-viewer の全画面を実際に操作し、表示データが正本 DB と一致するか、
細部の表示が破綻していないかを判定するための仕様書。

## 1. 目的と非目的

### 目的

1. **データ一致の検証** — 画面に出る値が正本 DB（Neon Postgres）と一致するか。
   `kouiso/skill-sheet` の `skillsheet.md` は移行元の参考記録であり、突合の一次情報ではない
   （詳細は「2. 検証環境」内「一次情報と正本の関係」を参照。#199）
2. **細部の破綻検出** — 欠落・重複・順序狂い・表崩れ・はみ出し・空表示
3. **画面としての成立** — 余白・整列・コントラスト・階層が破綻していないか

### 非目的

- デザイン正本（Figma / Claude Design）との pixel 単位の突合
- 性能測定・負荷試験
- セキュリティ診断（**ただし A-6a / A-6b の open redirect は機能回帰として実施する**。脆弱性の網羅的な洗い出しはしないが、
  既知の判定式が壊れていないかは毎回確認する）

### 検証に必要な環境変数

`.env.example`（リポジトリルート）を雛形に、少なくとも以下が要る。無いまま検証すると
特定のケースだけ「未実施」で終わり、次の巡回でも同じ設定不備を踏み直すことになる（#200）。

| 変数 | 用途 | 欠けると何が起きるか |
|---|---|---|
| `DATABASE_URL` | 正本 DB 接続（プール用 `-pooler` ホスト） | B/C/D 章の大半が実行不能 |
| `VIEWER_CODE` | 閲覧コード認証 | `/view` 系が開けない |
| `SESSION_SECRET` | 閲覧セッション cookie の HMAC | 同上 |
| `BETTER_AUTH_SECRET` | 編集者ログイン（Better Auth） | `/builder` が開けない |
| `BETTER_AUTH_URL` | Better Auth のオリジン検証 | Playwright 等 `localhost` 以外のホストで起動すると `Invalid origin` で editor ログインが失敗する |
| `SKILLSHEET_OWNER_ID` | 表示対象シートのオーナー id | `assertServerEnv()`（`app/layout.tsx` が無条件で呼ぶ）が起動直後に throw し、**全ルートが即クラッシュ**する（`ConfigErrorNotice` のような設定不備の案内には届かない。E-5b 参照） |
| `GITHUB_TOKEN` / `GITHUB_OWNER` / `GITHUB_REPO` | GitHub 経由の表示（`/view/[path]`、必須） | B-10b・B-13b-2・B-15b が未実施のまま終わる。値に改行文字（`\n`）が literal に混入していないことも確認する |
| `GITHUB_BRANCH` | 同上（任意。未設定時は `main`） | 同上 |

`GITHUB_FILE_PATH` は `/view/[path]` の実行時には参照されない（`packages/db/src/skillsheet.ts` の
DB シード取り込みスクリプト専用）。「GitHub 経由の表示に必要」と誤って案内していたのを訂正（Codex レビュー指摘）。
| `REVALIDATE_SECRET` | `POST /api/revalidate` の認証 | このエンドポイントの検証ができない |

GitHub トークンは失効することがある。`/view/[path]` 系が原因不明で止まったら、まず
`GET https://api.github.com/user` をそのトークンで直接叩いて 401 が返らないか確認する。

### 一次情報と正本の関係

```text
kouiso/skill-sheet/skillsheet.md   ← 移行元データ（かつての一次情報。現在は参考記録）
          ↓ インポート（1回限りの移行。以後は更新されない）
Neon Postgres (skill_sheets / blocks) ← 正本（アプリが読み、編集画面で更新される）
          ↓ blocksToMarkdown
     画面表示 / PDF出力
```

**DB（Neon Postgres）を一次情報とする。** `skillsheet.md` は移行時点の元データであり、
それ以降 DB 側で追加・修正された内容（編集画面からの更新、スキル一覧の正規化・追加等）を
反映していない。また `skillsheet.md` にはスキルマトリクスのような集約済み節が存在せず、
案件ごとの技術スタック表から人が数え直した値と DB の値を単純比較すると、表記ゆれや
集計方法の違いをそのまま「欠落」として誤検出する（2026-08-08 の巡回で実際に発生：
スキル件数 39 件 vs 46 件、案件タイトルの `scope` 分離。どちらも DB 側から機械的に
`skillsheet.md` を検索すると全件の痕跡が見つかり、情報の欠落ではなかった。#199）。

画面系のケース（B 章）のデータ突合は **正本 DB → 画面** の 2 点で行う。
`skillsheet.md` との差分は FAIL 理由にせず、気付いた場合は参考情報として記録するに留める。

**PDF の内容突合（D-2）は正本 DB → 画面 → PDF の 3 点**で行う。画面と PDF はどちらも同じ
`blocksToMarkdown` / 構造化ブロックを源にしているため、2 点だけを突き合わせても「両方から
同じデータが落ちている」状態を検出できない。3 情報源それぞれについて件数と中身を記録し、
どの段で差分が出たかを特定できる形で残す。

## 3. 判定基準（全ケース共通）

PASS は次を全て満たしたときのみ。

1. **データ一致** — 表示値が正本 DB と一致する（一次情報と正本の関係を参照。`skillsheet.md` との差は FAIL 理由にしない）。欠落・重複・順序狂い・文字化けなし。
   ただし**正準ラベルへの変換が定義されている項目は、変換後の値で比較する**（工程が該当。`packages/db/src/process.ts` の
   `EXACT_MATCH_MAP` が DB の `実装` を表示の `実装・単体` に、`運用・保守` を `保守・運用` に写す）。
   生値で比較すると仕様どおりの変換を不一致として数えてしまうので、**変換前と変換後の両方を記録**して
   次の巡回者が同じ基準で判定できるようにする
2. **レイアウト** — 横スクロールなし（`scrollWidth <= clientWidth`）。要素の重なり・はみ出し・見切れなし
3. **文字** — 折返し破綻なし。`undefined` / `null` / `NaN` / 裸の `-` が出ない
4. **状態** — ローディング・空状態・エラー状態が意味のある文言で出る
5. **コンソール** — **ブラウザの** `console.error` ゼロ。`warning` は記録して個別判断。
   サーバー側の標準出力はこの判定に含めないが、**エラー分岐を通したケースでは server ログも採り、
   ブラウザ側と分けて記録する**（例: `/view` の取得失敗分岐は `view/page.tsx` が意図的に
   `console.error` を出す。ブラウザ 0 件だけを書くと系全体が無音だったように読める）
6. **操作** — 押せるものは全て押し、期待どおりの結果になる
7. **見た目** — 撮影画像を必ず開いて確認し、余白・整列・コントラスト・階層を評価する

> BUG が 1 件でもあればそのケースは **FAIL**。「PASS ただしバグあり」は認めない。
> 撮影しただけ・メタデータを見ただけは検証にしない。

## 4. テストケース

### A. 認証・入口

| ID | ケース | 手順 | 期待 |
|---|---|---|---|
| A-1a | 未認証で `/view` | cookie なしで `/view` を開く | `/viewer-auth` へリダイレクトする。クエリの有無は問わない: 2026-08-04 時点の `requireViewer()` は `next` を付けないが、U-6（#155）でゲートが `next` を保持するよう直せば `?next=/view` が付く。**どちらも PASS**。判定するのは「`/viewer-auth` に飛ぶこと」と、`next` が付く場合に**内部パスであること**（外部 URL なら FAIL） |

| A-4 | ログイン誤り | 誤った email / password | 「メールアドレスまたはパスワードが正しくありません」 |

### B. 閲覧（Viewer） — データ突合の本体

| ID | ケース | 検証内容 |

### C. 編集（Builder）

| ID | ケース | 検証内容 |
|---|---|---|
| C-1 | 初期表示 | シート一覧・タイトル・ブロック一覧が DB と一致 |
| C-2 | ブロック追加 | Markdown / 表 / スキル / 職務経歴 を各 1 個追加する。**追加したら必ず一意な値を入力してから保存する** — Markdown と職務経歴は空のままだと `isBlockInputEmpty()`（`blocks.ts:373`）で保存時に意図的に drop されるため、既定値のまま流すと「正しい挙動を保存失敗と誤判定する」か「実データ入りブロックの永続化を確認しないまま PASS にする」かのどちらかになる。保存後の DB 行と、**リロード後のエディタ UI に入れた値が戻ること**まで見る（DB の行数だけ見ると、行は増えるのに編集 UI だけ壊れる退行を拾えない） |
| C-3 | 並べ替え | パレットからの投入と既存ブロックのドラッグ並べ替え。**ドラッグが成功したことだけで PASS にしない** — `handleDragEnd` はローカルの `items` を並べ替えるだけなので、保存シリアライズや `order` の更新だけが壊れていても画面上は成功して見える。**保存後の DB の `order`** と **リロード後の表示順**を、並べ替え前の順序と突合する |
| C-4 | ブロック削除 | 削除 → 保存 → リロードで消えている |
| C-5 | 自動保存 | 編集後に「保存済み（自動）」。オフライン時は「自動保存に失敗 — 保存ボタンで再試行」。**オンライン復帰だけでは自動リトライしない**のが実装の意図（`builder-client.tsx` が失敗時スナップショットを記録し、同一内容では再 arm しない＝1.5 秒ごとの無限リトライ防止）。復帰後は「手動保存」か「新しい編集」で保存が再開することを確認する |
| C-6 | 手動保存 | 保存ボタン → toast → リロードで反映 |
| C-7 | 案件エディタ | 会社追加・案件追加・技術タグ入力・工程選択・hidden トグル。**削除経路も必ず通す** — 案件削除（`project-nav.tsx` の `aria-label="案件を削除"`）と会社削除（`title="会社を削除"`）。どちらも確認ダイアログが出ること、承認後に DB へ反映されること、**会社削除では配下の案件もまとめて消えること**、リロード後も保持されることまで見る。検証は本シートではなく専用シートを作って行い、終わったらシートごと消す（削除ボタンの `aria-label` はタイトル依存で、既定タイトルのままだと本シートの削除ボタンと区別できない） |
| C-8 | hidden 反映 | hidden にした案件・会社がビューアと PDF から消える。バックアップ書き出しには残る |
| C-9 | 履歴 | 履歴ドロワーを開いて復元する。**復元しただけで PASS にしない** — 復元はローカル state を書き換えるだけで、永続化は通常の保存 / 自動保存の経路に乗る。復元後に「保存済み（自動）」または手動保存を確認し、**DB の中身かリロード後の表示**で復元後のデータが残っていることまで見る（シリアライズや自動保存が壊れていても、復元直後の画面だけなら正しく見える） |
| C-10 | 新規シート作成 | **`templates.ts` の初期ブロックを持つテンプレートを全部**作成し、定義ブロック数と保存後のブロック行数を突合する。2026-08-04 時点の対象は `profile`（技術者プロファイル）/ `full`（フルスキルシート）/ `console-dashboard`（ダッシュボード）の 3 つ。`blank`（空白）は 0 ブロックが正なので突合対象外。**full だけを作って PASS にしない**（#158 のように 1 テンプレートだけ初期ブロックが落ちる退行を取り逃すため）。テンプレートが増えたらこの一覧も更新する |
| C-11 | シート削除 | **一意なタイトル（またはシート ID）で検証用シートを特定してから**削除し、一覧と DB の両方から**対象の行だけ**が消えることを確認する。削除ボタンの `aria-label` は「「<タイトル>」を削除」でタイトル依存なので、既定タイトルのまま新規作成すると本シートの削除ボタンと区別できない（この取り違えで本シートを消しかけた実績あり） |
| C-12a | バックアップ書き出し（hidden 保持） | hidden にした案件・会社が出力に残る |
| C-12b | バックアップ書き出し（全データ） | 会社概要文を含め、DB が持つ情報が欠落せず出力される |
| C-13 | 離脱警告 | 未保存で離脱しようとすると警告が出る。**2 経路とも確認する** — (a) タブを閉じる/リロード（`beforeunload`）、(b) **SPA 内遷移**（シート切替・「閲覧へ」リンク）。(b) は `beforeunload` が発火せず `confirmDiscardChanges()` が別に守っているので、(a) だけで PASS にするとクライアント遷移だけが未保存編集を捨てる退行を見逃す。なお `AUTOSAVE_DEBOUNCE_MS` は 600ms なので、編集後に 1 秒待つと自動保存で dirty が解消してダイアログは出ない。未保存状態を保つにはオフラインにして自動保存を失敗させる |
| C-14a | 狭幅ナビ | 320 / 375px の初期表示で左ナビがレール → ドロワーに畳まれ、操作できる |
| C-14b | 狭幅のスキル表 | 320px でスキル表の列が潰れず、経験年数が読める |
| C-15a | 別窓プレビュー（同期） | `/builder/preview` が編集内容と同期する |
| C-15b | 別窓プレビュー（直接アクセス） | 未接続の状態に合った文言と空状態の案内が出る |

### D. PDF 出力

| ID | ケース | 検証内容 |
|---|---|---|
| D-1 | ダウンロード | ビューアから PDF 生成 → toast → ファイル取得 |
| D-2 | 内容突合 | 正本 DB・画面・PDF の 3 点で全案件・全スキル、**会社概要文（`CompanyInfo.note`）**、**および profile / stats（氏名・肩書き・自己PR・メタ情報・統計カードの値）**が一致（欠落なし）。profile / stats を明示するのは、PDF が `blocksToMarkdown()` 経由で `profileBlockToMarkdown()` / `statsBlockToMarkdown()` を通す別経路だからで、**画面側の B-3 / B-4 が通っていても PDF だけ落ちる**ことがある。画面と PDF が同じ欠落を共有していても PASS にしない。会社概要文を明示するのは、2026-08-04 時点でビューア・PDF・Markdown・バックアップのどの出力にも描画先が無く 18 社分が消えているため（D-3 / #139）。**バックアップだけ直った状態**でも PDF / ビューアが落とし続けていれば FAIL とする（C-12b はバックアップ経路しか見ない） |
| D-3 | ページ切れ | **3 種類とも確認する** — (a) セクション見出しと直後の本体（表・カード）が同じページに収まる、(b) 案件カードがページ境界で割れない、(c) スキル表がページ境界をまたがない。(a) を落とすと、見出しだけがページ末尾に取り残されて次ページ先頭から本文が始まる退行（P-2 / #147 の (a)）を次回取りこぼす。測り方は「PDF のテキストを描画順の 1 本の並びにして、対象の開始位置から次の対象の開始位置までが何ページにまたがるか」を見る（文字列がどのページに出るかで数えると、`React` のような語が他カードの技術スタックにも出て誤検出になる） |
| D-4 | 日本語フォント | NotoSansJP が適用され豆腐が出ない。**加えて、日本語に人工ハイフンが混入しないこと** — PDF の抽出テキストに `バックエンド・デー-` のような行末ハイフンや `【PatentStart-】` が出たら FAIL（P-1 / #146。`Font.registerHyphenationCallback` の未設定/誤設定で起きる）。フォント適用が正常でもこの退行は起きるので、豆腐の有無だけで PASS にしない |
| D-5a | hidden 除外（案件単体） | hidden にした案件が PDF に出ない |
| D-5b | hidden 除外（会社） | hidden にした**会社とその配下の案件**が PDF に出ない。実装は案件単体の `hidden` と会社の `hidden` を別条件で扱う（`filterVisibleProjectData` が `!item.hidden && !hiddenCompanyIds.has(item.companyId)`）ため、案件単体だけ確認して通すと会社側の退行を見逃す |

### E. 横断

| ID | ケース | 検証内容 |
|---|---|---|
| E-1 | 全画面 × 4 ビューポート × 2 テーマ | 横スクロール・重なり・見切れ・コントラスト |
| E-2 | dark テーマ | 全画面で文字が読める |
| E-3 | キーボード操作 | Tab でフォーカスが見え、主要操作に到達できる。**画面ごとに記録する**（`/login` / `/viewer-auth` / `/view` / `/view/db/:id` / `/builder` / `/builder/preview`）。ビューア 1 画面の結果で他画面を代表させない。測り方は「実キーボードの Tab で当て、ブラーも再フォーカスもせずに `:focus-visible` 時の `outline` / `box-shadow` を読む」。**`outline: auto` を「リング無し」と数えない**（Chromium の既定リングはこの値で出る）。フォーカス時とブラー時の計算値の差分、および要素だけを切り取った画素比較は、それぞれ transition の途中値・ボーダーボックス外のリングで誤判定するので使わない |
| E-4 | コンソール | 全画面で `console.error` ゼロ。HTTP 404 応答そのものに由来するものは除外し、それ以外は理由を記録する。**E-1 で撮った全ルートの件数をルートごとに書く**（`/view` / `/view/db` / `/view/db/:id` / `/view/db/<存在しない UUID>` / `/builder` / `/builder/preview` / `/login` / `/viewer-auth` / `/view/[path]` / 404）。一部のルートだけ挙げて残りを省略しない（省略した画面で後から `console.error` が出ても緑のままになるため） |
| E-5a | エラー画面（`error.tsx` / 404） | 意味のある文言で出る |
| E-5b | DB 取得失敗フォールバック | **env は present のまま接続先を到達不能にして**（`DATABASE_URL` / `SKILLSHEET_OWNER_ID` を外すと `app/layout.tsx` の `assertServerEnv()` が先に落ちてページ内の `try/catch` に届かない）、**`apps/web/.next` を丸ごと消した**単独起動で開く（`.next/cache` だけでは前回取得した内容の控えが残り、DB 到達不能でも 200 のまま古い内容が返り続けて 500 を再現できない。Issue #199 / #204 で判明）。**3 経路とも見る** — `/view`（一覧 / `getCachedDbSheets()`）、`/view/db`（デフォルトシート本文 / `getCachedDbSheet()`）、**`/view/db/:id`（実在する詳細 URL / `getCachedDbSheetById()`）**。ログ行も別で、それぞれ `Failed to fetch DB sheets:` / `Failed to load DB skill sheet:` / `Failed to load sheet:`。失敗の原因を 2 種類に分けて検証する。**(a) 設定不備**：`DATABASE_URL` / `SKILLSHEET_OWNER_ID` を未設定または未マイグレーション（`42P01` 等）にした場合、いずれの経路も `isConfigError()` 判定で `ConfigErrorNotice` を返して **200** になる（原因と対処が分かる文言がブラウザに出る）。**(b) 接続断**：env は present のまま接続先を到達不能にして `apps/web/.next` を丸ごと消した単独起動で開く。設定不備ではなく一時的な接続障害は 3 経路すべてで `console.error`（`Failed to fetch DB sheets:` / `Failed to load DB skill sheet:` / `Failed to load sheet:`）を出した上で `throw err` し、`error.tsx` へ委ねて **500** になる。3 経路でこの 2 種類の応答が食い違っていたら FAIL。**ブラウザとサーバーのログを分けて記録する**（両ページとも catch で `console.error` を必ず出すため、ブラウザ 0 件だけを書くと系全体が無音だったように読める） |

## 5. 記録フォーマット

各ケースについて次を記録する。

```text
[ケースID] 結果: PASS / FAIL / BLOCKED
  スクリーンショット: <path>（開いて確認済み）
  観察: 画面上の要素列挙 + レイアウト記述
  突合（画面系 B 章）: 正本 DB → 画面 の件数と中身 → どの段で差が出たか
  突合（D-2 のみ）: 正本 DB → 画面 → PDF の件数と中身 → どの段で差が出たか
  逸脱: BUG / COSMETIC の分類（最終判断はレビュアー）
```

## 6. 逸脱の扱い

- 原則 1 逸脱 = 1 Issue。`.github/ISSUE_TEMPLATE/bugfix.yml` / `feature.yml` の構成に合わせる
- ただし、単独では着手単位にならない小さな逸脱（同一ファイルの細部・同種のコントラスト不足など）は
  1 Issue にまとめてよい。まとめた場合は Issue 本文に逸脱を見出しで分けて列挙し、
  完了条件も逸脱ごとにチェックボックスを立てる（個別に潰せる状態を保つ）
- 期待挙動・実際の挙動・再現手順・スクリーンショットを必ず入れる
- 全 Issue を束ねる親 Issue（dogfooding 結果サマリ）を 1 本立てる
- 修正は別タスク。この仕様書の実行範囲は起票までとする

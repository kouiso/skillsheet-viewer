# Dogfooding テスト仕様書

skillsheet-viewer の全画面を実際に操作し、表示データが元データと一致するか、
細部の表示が破綻していないかを判定するための仕様書。

## 1. 目的と非目的

### 目的

1. **データ一致の検証** — 画面に出る値が元データ（`kouiso/skill-sheet` の `skillsheet.md`）および
   正本 DB（Neon Postgres）と一致するか
2. **細部の破綻検出** — 欠落・重複・順序狂い・表崩れ・はみ出し・空表示
3. **画面としての成立** — 余白・整列・コントラスト・階層が破綻していないか

### 非目的

- デザイン正本（Figma / Claude Design）との pixel 単位の突合
- 性能測定・負荷試験
- セキュリティ診断

## 2. 検証環境

| 項目 | 値 |
|---|---|
| ビルド | `pnpm build` → `pnpm start -p 3210`（本番ビルド。dev の HMR ノイズを避ける） |
| DB | Neon 本番プロジェクト `skillsheet-viewer` からのコピーブランチ（本番には書かない） |
| ブラウザ | Chromium（Playwright） |
| ビューポート | 320×800 / 375×812 / 768×1024 / 1280×800 |
| テーマ | light / dark |
| 証跡 | `test-results/dogfooding/<case-id>-<viewport>-<theme>.png` |

### 元データと正本の関係

```
kouiso/skill-sheet/skillsheet.md   ← 元データ（人が書いた一次情報）
          ↓ インポート
Neon Postgres (skill_sheets / blocks) ← 正本（アプリが読む）
          ↓ blocksToMarkdown
     画面表示 / PDF出力
```

データ突合は **元データ → 正本 → 画面** の 3 点で行う。
正本と画面が一致していても、元データから欠落していれば FAIL とする。

## 3. 判定基準（全ケース共通）

PASS は次を全て満たしたときのみ。

1. **データ一致** — 表示値が元データ・正本と一致する。欠落・重複・順序狂い・文字化けなし
2. **レイアウト** — 横スクロールなし（`scrollWidth <= clientWidth`）。要素の重なり・はみ出し・見切れなし
3. **文字** — 折返し破綻なし。`undefined` / `null` / `NaN` / 裸の `-` が出ない
4. **状態** — ローディング・空状態・エラー状態が意味のある文言で出る
5. **コンソール** — `console.error` ゼロ。`warning` は記録して個別判断
6. **操作** — 押せるものは全て押し、期待どおりの結果になる
7. **見た目** — 撮影画像を必ず開いて確認し、余白・整列・コントラスト・階層を評価する

> BUG が 1 件でもあればそのケースは **FAIL**。「PASS ただしバグあり」は認めない。
> 撮影しただけ・メタデータを見ただけは検証にしない。

## 4. テストケース

### A. 認証・入口

| ID | ケース | 手順 | 期待 |
|---|---|---|---|
| A-1 | 未認証で `/view` | cookie なしで `/view` を開く | `/viewer-auth` へリダイレクト。`requireViewer()` は `next` を付けないので、クエリなしが現行の正しい挙動 |
| A-2 | 閲覧コード誤り | 誤ったコードで認証 | エラー文言が出る。画面が壊れない |
| A-3 | 閲覧コード正 | 正しいコードで認証 | `next` のパスへ戻る |
| A-4 | ログイン誤り | 誤った email / password | 「メールアドレスまたはパスワードが正しくありません」 |
| A-5 | ログイン正 | 正しい credential | `/builder` へ遷移 |
| A-6 | open redirect | `/login?next=//evil.com` | 外部へ飛ばず `/builder` へ |
| A-7 | ログアウト | `/api/logout` | セッション破棄。再度ゲートが効く |

### B. 閲覧（Viewer） — データ突合の本体

| ID | ケース | 検証内容 |
|---|---|---|
| B-1 | `/view` 一覧 | シート枚数・タイトル・更新日時が DB と一致。空/エラー状態の文言 |
| B-2 | `/view/db/:id` 初期表示 | トップバーに profile の氏名・所属会社。4 ビュー全 ON |
| B-3 | profile 突合 | 氏名・肩書き・自己PR・強み・年齢・勤務形態・最寄り駅・学歴を元データの「技術者プロファイル」節と 1 項目ずつ突合 |
| B-4 | stats 突合 | 4 枠の数値と単位が元データの記述と矛盾しない |
| B-5 | skills 突合 | 全カテゴリ × 全スキルの「名称・年数・習熟度」を元データのスキル表と全件突合。件数も一致させる |
| B-6 | 案件件数突合 | 画面の会社数・案件数を数え、正本 DB および元データの `### ◆` セクション数と突合。差があれば真因を特定する |
| B-7 | 案件詳細突合 | 全案件について 期間・役割・規模・チーム・技術スタック・担当工程・業務内容・習得スキルを元データと突合（サンプリング禁止・全件） |
| B-8 | 期間表記 | 期間・年数の表示が元データと一致。「継続中」案件の表記 |
| B-9 | ビュートグル | スキルマトリクス / 工程の俯瞰 / 案件詳細 / タイムライン を個別 OFF→ON。全 OFF 時の見た目 |
| B-10 | 目次（TOC） | 項目が見出しと一致。スクロールでアクティブ見出しが追従。**対象は markdown 由来の見出しを持つシート（`/view/[path]`）のみ。** ダッシュボード（構造化ブロックのみ）は `SectionHead` が意図的に id を付けず `headings.length === 0` で TOC を描画しないため対象外 |
| B-11 | 技術フィルタ | 絞り込みで該当案件のみ残る。0 件時の表示 |
| B-12 | 工程ステッパー | 表示される工程が案件の `process` と一致 |
| B-13 | Markdown 描画 | GFM 表が表として描画される（`:---:` の生テキスト露出なし）。`<details>` の開閉 |
| B-14 | 存在しない ID | `/view/db/<random-uuid>` で 404 ページ |
| B-15 | `/view/[path]` | GitHub 連携未設定時に 500 でなく案内が出る |
| B-16 | `/compare` | a/b 欠落時は `/view` へ。2 枚並列表示。狭幅で縦積み |

## 5. 記録フォーマット

各ケースについて次を記録する。

```
[ケースID] 結果: PASS / FAIL / BLOCKED
  スクリーンショット: <path>（開いて確認済み）
  観察: 画面上の要素列挙 + レイアウト記述
  突合: 元データ側の値 → 画面側の値 → 一致 / 不一致
  逸脱: BUG / COSMETIC の分類（最終判断はレビュアー）
```

## 6. 逸脱の扱い

- 1 逸脱 = 1 Issue。`.github/ISSUE_TEMPLATE/bugfix.yml` / `feature.yml` の構成に合わせる
- 期待挙動・実際の挙動・再現手順・スクリーンショットを必ず入れる
- 全 Issue を束ねる親 Issue（dogfooding 結果サマリ）を 1 本立てる
- 修正は別タスク。この仕様書の実行範囲は起票までとする
